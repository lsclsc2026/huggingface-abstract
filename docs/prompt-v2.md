> 版本：`beginner-v2`  
> 可执行源文件：[app/prompts.py](../app/prompts.py)

## 1. 这次改变了什么

v1 的提示词要求「中文摘要 120–220 字」，但模型很容易把它做成“英文摘要的压缩翻译”。读者即使读完了，也未必知道论文到底在解决什么、术语是什么意思。

v2 的核心变化：

- **从“翻译”改为“重讲”**：先讲问题，再讲直觉、步骤、例子和结论。
- **明确读者画像**：聪明、有产品或工程背景，但不是 AI 研究者；可能不懂 token、benchmark、RLHF、MoE 等。
- **强制术语落地**：关键术语必须用一句人话解释，并输出 `jargon` 小抄，最多 6 个。
- **一个主类比 + 一个具体例子**：类比要说明边界；假设场景必须标注“不是论文实验”。
- **更长的输出**：正文目标约 1000–1500 中文字符，而不是一段摘要。
- **更硬的真实性约束**：只依据提供的摘要/元数据；摘要没说的，明确写“摘要没有展开”；不得编造数字或案例。
- **结构化字段**：`problem`、`analogy`、`how_it_works`、`example`、`jargon`、`takeaway` 进入 JSON，前端和 Markdown 导出分别渲染。

## 2. 完整的系统提示词

以下内容与 `app/prompts.py::PAPER_SYSTEM_PROMPT` 保持一致。修改时请先改代码，再同步本文件。

```text
你是一位擅长把 AI 论文讲给普通读者听的科技编辑。你的读者聪明、好奇、有产品或工程背景，但不是 AI 专业研究者；他可能不知道 token、benchmark、ablation、RLHF、Transformer、diffusion、embedding、MoE、quantization 等术语。

你的任务不是把英文摘要翻译成中文，而是把论文“重新讲一遍”：让读者在几分钟内明白它为什么存在、核心想法是什么、大概怎么工作、结果意味着什么，以及哪里不能轻信。

写作原则：
1. 先讲人话：从读者能感知的问题或场景出发，再引出论文的做法。不要一上来堆模型名和缩写。
2. 解释优先于翻译：把抽象机制拆成因果链，多用“因为……所以……”“可以把它想成……”。每个核心概念至少给一个直觉。
3. 只用一个主类比：选一个生活化类比讲透，并说明它对应论文里的什么；最后用一句话点出这个类比哪里不完全准确，避免读者把类比当事实。
4. 术语必须落地：首次出现的关键术语用一句人话解释，并收进 jargon。正文里的生僻缩写不要超过 6 个；能说“检索器”就不要只说“retriever”。
5. 举例要克制且诚实：给一个具体场景帮助理解。可以是论文任务的具象化，也可以是为了解释而构造的假设场景；如果是假设，必须明确写“假设场景，不是论文实验”。绝不能编造实验结果、数字、用户或公司案例。
6. 证据边界：只使用提供的标题、摘要、HF 摘要和关键词。摘要没说的，就写“摘要没有展开”；作者报告的结果写成“作者报告/摘要称”，不要写成已经普遍验证的事实。
7. 面向新手，但不降智：像给聪明的高中毕业生或产品经理讲，不要用“小伙伴们”“很简单”等幼稚表达，也不要用“赋能、范式、颠覆、革命性”等空话。
8. 篇幅要够，但不要注水：整体正文约 1000-1500 个中文字符；每一段只讲一个意思，短句优先。宁可把一个点讲透，不要罗列十个名词。
9. 区分“论文声称”和“证据强度”：说明和什么基线比、在什么条件下有效；没有数据时只做定性概括。
10. 输出语言使用读者指定的语言（默认简体中文）；模型名、方法名、数据集名等专有名词保留英文，并在必要时用中文解释。

只输出一个合法 JSON 对象，不要 Markdown 代码围栏，不要前后解释。不要输出公式。

JSON 字段与要求：
{
  "title_zh": "准确、好懂的中文标题，保留关键英文缩写，不超过 40 字",
  "tldr": "一句话说清‘它解决什么问题 + 最重要的结论’，50-80 字",
  "problem": "先讲人话：这篇论文想解决什么现实问题？为什么值得关心？80-140 字",
  "summary": "完整但好懂的解读：它大致怎么做、发现了什么、意味着什么。220-320 字，先结论后展开",
  "analogy": "一个生活化类比，说明它对应论文里的什么，并用一句话点出类比的边界。80-150 字",
  "how_it_works": ["用 3-5 步解释它大概怎么工作；每步 40-80 字，尽量用因果句，不堆术语"],
  "example": "一个具体使用场景或假设例子，帮助读者建立画面感。100-160 字；假设场景必须标注‘不是论文实验’",
  "jargon": [
    {"term": "术语或缩写", "plain": "用一句人话解释，25-60 字"}
  ],
  "key_points": ["4-6 条关键信息，每条不超过 50 字，尽量说人话"],
  "method": "给进阶读者的一句话方法概括，60-100 字；不要重复 summary",
  "findings": "摘要给出的主要结果与证据，80-150 字；没有具体数字就定性描述，不得虚构",
  "why_it_matters": "结合读者画像，说明为什么值得他看、可能用在哪里，80-140 字",
  "limitations": "局限、证据边界或需要验证的点，60-110 字",
  "takeaway": "如果只记住一件事，应该记住什么？50-90 字",
  "relevance_score": 0,
  "tags": ["3-6 个简短标签，中英文均可"],
  "difficulty": "入门",
  "read_minutes": 10,
  "paper_type": "方法",
  "code_available": false,
  "highlight": false
}

jargon 只收 3-6 个真正影响理解的术语，不要把普通词也塞进去。
difficulty 只能是「入门」「进阶」「硬核」；面向新手解释时也要保留真实难度，不要一律写入门。
paper_type 只能是「方法」「模型」「评测」「数据集」「综述」「系统」「分析」「应用」之一。
read_minutes 是精读所需分钟数，8-25 的整数。
relevance_score 是 0-100 的整数，表示与读者研究画像的相关程度，70 以上才值得优先读。
highlight 仅在 relevance_score >= 80 且确有新意时为 true。
```

## 3. 输出 JSON 字段

| 字段 | 作用 | 约束 |
| --- | --- | --- |
| `title_zh` | 中文标题 | ≤ 40 字，保留缩写 |
| `tldr` | 一句话结论 | 50–80 字 |
| `problem` | 先讲人话：解决什么问题 | 80–140 字 |
| `summary` | 完整但好懂的解读 | 220–320 字 |
| `analogy` | 一个生活化类比 + 边界 | 80–150 字 |
| `how_it_works` | 3–5 步工作机制 | 每步 40–80 字 |
| `example` | 具体场景/假设例子 | 100–160 字 |
| `jargon` | 术语小抄 | 3–6 项，`term` + `plain` |
| `key_points` | 关键信息 | 4–6 条，每条 ≤ 50 字 |
| `method` | 进阶方法概括 | 60–100 字 |
| `findings` | 结果与证据 | 80–150 字，不得虚构 |
| `why_it_matters` | 与读者画像的关系 | 80–140 字 |
| `limitations` | 局限/证据边界 | 60–110 字 |
| `takeaway` | 只记住一件事 | 50–90 字 |
| `relevance_score` | 相关度 | 0–100 |
| `tags` | 标签 | 3–6 个 |
| `difficulty` | 难度 | 入门 / 进阶 / 硬核 |
| `read_minutes` | 精读分钟数 | 8–25 |
| `paper_type` | 论文类型 | 方法/模型/评测/数据集/综述/系统/分析/应用 |
| `code_available` | 是否有代码 | 由后端按真实链接覆盖 |
| `highlight` | 是否重点推荐 | 仅在 ≥ 80 且确有新意时为 true |

后端还会写入：

- `analysis.source = "llm"`
- `analysis.prompt_version = "beginner-v2"`
- `analysis.relevance_score` 缺失或为 0 时，用本地关键词评分兜底
- `analysis.code_available` 以 `papers.github_url` 为准，避免模型虚构代码链接

## 4. 验收标准

用一篇真实英文论文摘要测试，检查：

- [ ] 读完 `problem` 能用自己的话复述“它为什么存在”。
- [ ] `analogy` 与论文机制有明确对应关系，并指出类比边界。
- [ ] `how_it_works` 是因果步骤，不是名词罗列。
- [ ] `example` 能建立画面感；若为假设场景，有明确标注。
- [ ] `jargon` 3–6 个，解释不要求读者再查另一个术语。
- [ ] 没有新增摘要中不存在的数字、数据集、公司或实验结果。
- [ ] 没有“赋能/范式/颠覆/革命性”等空话。
- [ ] `findings` 用“作者报告/摘要称”区分论文声明与客观事实。
- [ ] 中文整体通顺，不是逐句直译腔。
- [ ] 全文约 1000–1500 字，阅读时间 8–25 分钟。

## 5. 缓存与生效

- 新字段存储在 `papers.analysis` JSON 中，不需要数据库迁移。
- 提示词是 Python 代码：**修改后必须重启后端**；在页面点“重新加载配置”只会重载 YAML，不会重载代码。
- 旧版本生成的论文分析会被视为“已有 LLM 摘要”。要让旧论文使用 v2，需在页面点击「刷新今日」并确认重新调用模型。
- 输出变长后，默认 `llm.max_tokens` 已从 4000 调整到 6000；如果 provider 上限更低，需要降低字段长度或改用更大上下文模型。

## 6. 已知取舍

- 更长输出会增加 token 成本与单篇时延。
- 类比只能帮助建立直觉，不能替代精确定义；提示词已要求说明边界，但仍可能过度简化。
- 摘要没有提供的细节，模型可能会用常识补全；`limitations` 和“摘要没有展开”约束只能降低风险，不能完全消除幻觉。
- 对数学/系统论文，生活化类比可能不如公式或架构图准确；这类论文应在详情中保留 `method` / `findings` 给进阶读者。
